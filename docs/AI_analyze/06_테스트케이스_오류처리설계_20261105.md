## 6. 오류 처리 설계

### 6-1. 원칙
1. **분류 → 기록 → 계속**: 파일 오류는 그 파일만 ERROR, 작업 오류는 그 작업만 FAILED, 실행 전체를 멈추는 것은 "출력 불가·저장공간 부족·사용자 중지"뿐.
2. **취소는 오류가 아니다**: `CancellationException` 은 항상 다시 던진다. 마무리 쓰기는 `withContext(NonCancellable)`.
3. **모든 catch 는 기록**: 코드(`E-…`)·메시지를 `_app_log.txt` 와 Logcat(`GoogleStt`)에 남긴다. 조용히 삼키는 `runCatching {}` 금지(1단계 위험 6).
4. **서버 실패 규칙 따름(D28 확정)**: 실패한 파일은 `<이름>.txt` 를 만들지 않고 `<이름>.ERROR.txt` 에 첫 줄 `[ERROR] <원인 한 줄>` (+ 부분 결과 참고 줄)을 쓴다. 성공·무음 저장 때는 묵은 `.ERROR.txt` 를 지운다. 서버 `stt_common.save_failure`/`save_transcript` 와 같은 규칙 → PC 평가기가 실패를 무음으로 오인하지 않는다.
5. **사용자 문구는 `strings.xml`**, 원인 + 할 일 1개를 함께 보인다.

### 6-3. `note` 열 코드 규칙
- 형식: `코드[:짧은 원인]`, 여러 개면 `;` 로 잇는다. 예 `ERR_TIMEOUT;WARN_NET_DELTA`.
- 정상 정보도 같은 칸: VAD 프리셋 요약, `[상업 조건부]`, `download_overlap`(device.csv 쪽).
- 코드 목록은 `AppError` 와 같은 파일에 상수로 둔다(문서·코드 한 곳).

### 6-4. 로그 규칙
- Logcat 태그 `GoogleStt`, 화면 로그와 같은 문장. 디버그 줄은 `[D]` 접두어(화면에서 숨김 가능).
- `_app_log.txt`: 출력 폴더, 20 MB 넘으면 `_app_log.1.txt` 로 돌림(1개 보관).
- 기록 금지: 토큰·비밀값(현재 없음), 사용자 음성 내용 외의 개인정보.
