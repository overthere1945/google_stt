## 2. T2 며칠 연속 실행 — 포그라운드 서비스·전원

### 2-1. 확인 사실
| 사실 | 출처 |
|---|---|
| Android 14+ 는 `foregroundServiceType` 선언 필수, 유형별 권한 필요 | FGS service types |
| `dataSync`·`mediaProcessing` 은 targetSdk 35 이상에서 **24시간 중 6시간** 제한, 넘으면 `Service.onTimeout()` 호출 후 정지 요구 | FGS timeout |
| `specialUse` 는 `FOREGROUND_SERVICE_SPECIAL_USE` 권한 + `<property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE" android:value="..."/>` 선언. 문서상 시간 제한 없음(Play 배포 시 심사 사유 필요 — 이 앱은 내부 평가용이라 해당 없음) | FGS service types |
| 포그라운드 서비스는 CPU 를 깨워 두지 않는다 → 화면 꺼짐 중 계속 계산하려면 `PARTIAL_WAKE_LOCK` 필요. 오래 잡은 wake lock 은 Play vitals "stuck wake lock" 대상(배포 안 하므로 영향 없음, 단 작업 끝나면 반드시 해제) | wake lock 가이드 |
| Samsung One UI: 오래 안 쓴 앱은 "잠자는 앱"→"깊은 잠자는 앱"으로 옮겨 백그라운드 동작 제한. 예외 목록 "절대 잠자지 않는 앱" | Samsung 앱 관리 문서 |

### 2-2. 결정안
| 항목 | 값 |
|---|---|
| 서비스 유형 | `specialUse`, subtype 값 `"On-device STT batch evaluation (long-running, user-started)"` |
| 권한 | `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, `POST_NOTIFICATIONS`, `WAKE_LOCK`, `INTERNET`, `ACCESS_NETWORK_STATE`, `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`(사이드로드 전용 — 예외 요청 창 띄우기) |
| wake lock | 작업 실행 중에만 `PARTIAL_WAKE_LOCK` 획득, 작업 사이 발열 대기·완료·중지 시 해제. 타임아웃 붙인 획득(예: 작업당 상한) 후 갱신 |
| 화면 | 실행 대시보드에서 "화면 켜 두기" 선택(기존 v2.5.0 확정 사양 계승) |
| 시작 전 점검 화면 | ① 알림 권한 ② 배터리 최적화 예외 여부(`isIgnoringBatteryOptimizations`) ③ 충전 연결 여부 ④ "절대 잠자지 않는 앱" 안내 버튼(설정 화면으로 이동) |
| ❓ 실기기 | S24 Ultra 에서 24시간 이상 연속 실행 시험(화면 끔·충전 중) — 8단계 장시간 시험 항목 |

### 2-3. 사용자 설정 절차(One UI — 꼬리 질문 3 답)
1. **설정 → 애플리케이션 → (앱) → 배터리 → "제한 없음"** 선택.
2. **설정 → 디바이스 케어 → 배터리 → 백그라운드 사용 제한 → "절대 잠자지 않는 앱"** 에 앱 추가. 같은 화면의 "사용하지 않는 앱을 절전 상태로 전환"을 꺼도 된다.
3. 앱 첫 실행 때 뜨는 "배터리 최적화 무시" 요청에 **허용**.
4. 실행 중에는 **충전기 연결**, 발열 SEVERE 이상이면 앱이 스스로 대기(기존 규칙 30초 확인·최대 20분).
- 메뉴 이름은 One UI 판마다 조금 다르다. 앱은 설정 화면 진입 버튼과 문구만 제공하고, 실제 등록은 사용자가 한다(앱이 대신 바꿀 수 있는 공개 API 없음).

## 3. T3 모델·VAD 자동 다운로드

### 3-1. 다운로드 경로 — 사용자 결정 **A + B 병행**
| 방법 | 설명 |
|---|---|
| A. 외부망 직접 | 휴대폰(S24 Ultra 또는 S25 Ultra)이 외부망에서 앱 안 다운로드. 회사 Wi‑Fi(HTTPS 검사)는 앱이 시스템 CA 만 믿으므로 TLS 오류 → 앱이 "회사망 인증서 문제 가능" 으로 구분 안내 |
| B. PC 에서 받아 가져오기 | PC 스크립트(기존 `tools/download_stt_models.sh`·`download_models.sh` 확장)로 받은 폴더를 휴대폰 `Documents/stt_assets/` 로 복사 → 앱 [가져오기]가 SAF 로 읽어 앱 전용 저장소로 복사하며 SHA256 검증 |

### 3-2. GitHub 릴리스 동작(실측)
- `github.com/k2-fsa/sherpa-onnx/releases/download/asr-models/<파일>` → **302** → `release-assets.githubusercontent.com` 서명 URL(유효 약 1시간) → Range 요청 시 **206 Partial Content**, `Accept-Ranges: bytes`.
- 이어받기 규칙: 끊기면 **GitHub 원래 URL 부터 다시 요청**(만료된 서명 URL 재사용 금지), `Range: bytes=<받은 크기>-`, 응답이 200 이면 처음부터, 206 이면 `Content-Range` 시작 값이 받은 크기와 같은지 확인.
- 구현: `HttpURLConnection`(https→https 리다이렉트 자동 따라감) — OkHttp 추가 의존성 불필요(단순성 원칙).

- 압축 파일 안에는 쓰지 않는 fp32 파일도 들어 있다 → **필요한 파일(int8·tokens 등)만 풀고 압축 파일은 즉시 삭제**. 다운로드 중 최대 사용량 = 압축 파일 + 풀린 파일이므로 여유 공간 검사는 "압축 크기 × 2 + 1 GB" 로 잡는다.
- Vosk(alphacephei.com zip): 이 작업 환경에서는 접속 차단(403)으로 실측 못 함 → ❓ 첫 다운로드 때 앱이 `Content-Length` 기록.
- VAD 파일(Silero·pyannote·FSMN·FireRed·TEN)은 기존 `tools/download_models.sh` 의 URL·커밋 고정과 `assets/models.sha256` 해시를 그대로 쓴다(재검증 끝난 값).

### 3-4. SHA256 고정 방식
- PC 에서 스크립트로 1회 받아 **압축 파일 SHA256 + 풀린 파일별 SHA256** 를 계산해 `app/src/main/assets/asset_manifest.json`(가칭)에 커밋 → 앱은 이 값과 대조. 값이 없는 자산은 "미검증" 표시하고 실행은 허용하되 `run_meta` 에 기록.
- `asset_manifest.json` 은 3단계 산출물이 아니라 5·7단계 작업(PC 에서 스크립트 실행 필요).

### 3-5. tar.bz2 해제
| 후보 | 판정 |
|---|---|
| Apache Commons Compress **1.28.0**(2025-07-29, Apache-2.0) `TarArchiveInputStream` + `BZip2CompressorInputStream` | ✅ 채택. 순수 Java, Android 플랫폼 소스에도 포함되어 쓰임 |
| 직접 구현 | ❌ 불필요한 위험 |
- ⚠️ bzip2 는 단일 스레드 해제라 whisper-medium(1.9 GB) 같은 큰 파일은 수 분 걸릴 수 있다 → 다운로드·해제는 "시간 측정 모드"에서 작업 사이(스케줄러 일시 정지)에만 수행(4-2 참고).

## 8. T8 예상 소요 시간(ETA)

### 8-1. 계산식
- 작업 1개 = Σ(파일 길이 `audio_sec`) × RTF(엔진, 기기, 모드) + 모델 적재 시간 + 파일당 고정 부담(디코딩·VAD·저장).
- 모드별 RTF:
  - 오프라인 sherpa(공급 없음): 학습된 `rtf` 값.
  - 스트리밍·Vosk: Feed 사용 안 함 → 학습된 `rtf`, Feed 사용 → 공급 시간(파일 길이 × 지연/100ms) + tail.
  - ML Kit: 파일 길이 × 1.0 + 세션 간 간격 + 세션 한도로 인한 묶음 대기.
- 전체 = 작업 합 ÷ 동시 작업 수(동시 실행 시 측정된 감속 계수 반영) + 발열 대기 실측 평균.

### 8-2. RTF 출처 우선순위(꼬리 질문 4 답)
1. **같은 기기 실측**(키 = `Build.MODEL` + `Build.SOC_MODEL`, API 31+) — 엔진×VAD군별 지수 이동 평균.
2. **빠른 측정**: 실행 전 엔진별 가장 짧은 파일 1개를 NOVAD 로 돌려 RTF 측정(선택 버튼, 결과는 버림).
3. 다른 기기 실측: **섞지 않고** "S25 Ultra 기준 참고값" 으로 따로 표시만.
4. 아무 값도 없으면 "미측정" 표시(근거 없는 추정치를 만들지 않음).
- 이유: SoC·발열 특성이 달라 RTF 를 섞으면 두 기기 모두에서 틀린 값이 된다. 기기별로 저장하면 나중에 기기 비교 자료로도 쓴다.
- 참고 실측(기존 기록): S22 Ultra zipformer-ko 오프라인 RTF 0.025(customer 01, 84.1 s), nemotron 3.5-560ms REALTIME 은 공급 시간 ≈ 파일 길이.

### A-2. whisper.cpp q5/q8 와 sherpa int8 Whisper 를 같은 기준으로 비교?
- **같은 기준이 아니다.** 세 가지가 동시에 다르다.
  1. 런타임: ONNX Runtime vs ggml.
  2. 양자화: sherpa int8 = `onnxruntime.quantization.quantize_dynamic`, `op_types_to_quantize=["MatMul"]`, `QuantType.QInt8`(인코더·디코더의 MatMul 가중치만 int8, 활성값은 실행 중 동적 양자화). whisper.cpp q8_0 = 32개 가중치 블록마다 fp16 배율 1개(약 8.5 bit/가중치), q5_0 = 5 bit + 배율(약 5.5 bit), q5_1 = 5 bit + 배율 + 최솟값(약 6.0 bit).
  3. 디코딩: sherpa greedy vs whisper.cpp beam 5 + 온도 대체.
- v4.1.0 비교 설계(안): whisper.cpp 를 **q8_0** 기본(int8 에 가장 가까움)으로 두 조건 실행 — `greedy`(beam 끔·best_of 1·온도 대체 끔, sherpa 와 같은 디코딩) / `fw`(faster-whisper 기본값). 이렇게 하면 "런타임+양자화 차이"(sherpa int8 greedy ↔ whisper.cpp q8_0 greedy)와 "디코딩 차이"(greedy ↔ fw)를 나눠 볼 수 있다. q5 는 속도가 필요할 때만, fp16 은 tiny~small 참조용. `model`·`compute_type` 열에 `ggml-q8_0` 등으로 기록.

### A-3. bz2 해제가 느리면 Hugging Face 낱개 파일로?
- **일부 모델만 가능.** 확인 결과 `csukuangfj/sherpa-onnx-whisper-medium` 은 `medium-encoder.int8.onnx`·`medium-decoder.int8.onnx`·`medium-tokens.txt` 를 낱개로 제공(2024-07-13 갱신), `csukuangfj/sherpa-onnx-nemotron-speech-streaming-en-0.6b(-int8)-2026-01-14` 존재. 그러나 Qwen3-ASR 은 검색 결과 없음, 앱이 쓰는 nemotron-3.5 다국어 판도 찾지 못함 → 모든 모델을 바꿀 수는 없다.
- 위험: 같은 이름이라도 GitHub 압축 파일과 재수출 시점이 다를 수 있다(예: sherpa 1.13.5 에서 nemotron-3.5 재수출). → 출처와 관계없이 **풀린 파일 SHA256** 을 매니페스트에 고정하면 일관성 보장.
- HF 이어받기(Range): 이 작업 환경에서 HF 접속이 차단되어 실측 못 함 ❓.
- 결정안: ① 7단계에서 S24 Ultra 로 whisper-medium bz2 해제 시간을 먼저 잰다(해제는 모델당 1회뿐). ② 느리면 **B 방법(PC 에서 풀어서 낱개 파일을 옮기고 앱은 복사+SHA256 검증만)** 을 기본으로 한다 — 휴대폰에서 bz2 를 아예 하지 않음. ③ HF 낱개 파일은 있는 모델에 한해 선택 출처로 추가.

### A-4. Claude Code 로 직접 빌드·테스트, 이 대화를 넘길 수 있나

- PC3 에 Claude Code(CLI)를 설치해 `google_stt` 폴더에서 실행하면: `./gradlew assembleDebug`·`test`(JVM 단위 시험)·`lint`, USB 디버깅 연결 시 `adb install`·`adb logcat`·`adb exec-out screencap`(화면 캡처 확인)·`connectedAndroidTest` 까지 직접 실행·검증 가능.
- 이 대화 그대로 옮기기: `claude --teleport` 는 **GitHub 저장소에 연결된 클라우드 세션**을 같은 저장소 checkout 으로 가져오는 기능(깨끗한 git 상태·브랜치 push·같은 계정 필요). 이 대화는 저장소 없이 시작된 작업이라 해당하지 않을 것으로 본다.
- 권장: 문서 기반 단계(4~6단계)는 이 대화에서 진행 → 7단계 구현부터 PC3 Claude Code 로 이어감. 이어받기용으로 저장소 루트 `CLAUDE.md`(코드 규칙·서버 수정 금지·단계 문서 위치) + HANDOFF 문서를 만들어 두면 로컬 Claude Code 가 자동으로 읽는다. 원격 조종은 Remote Control(`/remote-control`)로 휴대폰·브라우저에서 가능.
- 회사망: Claude Code 는 `api.anthropic.com`·`claude.ai`·`platform.claude.com` 접속이 필요하고, HTTPS 검사 프록시는 OS 인증서 저장소에 회사 루트 인증서가 있으면 그대로 동작, 아니면 `NODE_EXTRA_CA_CERTS` 로 지정. 회사 PC 에 설치해도 되는지는 사내 보안 규정 확인 필요.
